Mission 1: The Bridge & The Fetch

Clients, Servers, and APIs

What are they?

Imagine you're at a restaurant. You, the Client, want food. The kitchen, the Server, has the food and knows how to prepare it. But you can't just walk into the kitchen. You need a way to communicate. That's where the waiter comes in. The waiter is the API (Application Programming Interface).

You look at a menu (the API documentation), give your order (a request) to the waiter (the API), who takes it to the kitchen (the Server). The kitchen prepares your food and gives it back to the waiter (the API), who brings it to your table (a response).

In web development:

  • Client: Your browser (Chrome, Firefox, etc.) running JavaScript code.
  • Server: A powerful computer somewhere on the internet that stores data and runs applications.
  • API: A set of rules and protocols that allows your client-side code to request data from a server. It's the "contract" for how two pieces of software talk to each other.

Why do we need them?

We need this separation to build dynamic, powerful applications. Your browser can't possibly hold all the data in the world (like all of GitHub's user data or every Pokémon). Instead, it acts as a lightweight interface that requests just the data it needs, when it needs it, from a server that is designed to store and manage that data efficiently.

How do we use them?

We use a built-in browser function called fetch(). We give it a URL (the "address" of the API endpoint on the server), and it sends a request over the internet. The server then sends back a response, usually containing the data we asked for.

JSON Review

What is JSON?

JSON (JavaScript Object Notation) is the language of APIs. While your JavaScript code loves working with full-featured objects, you can't send a complex object directly over the internet. You need to convert it into a simple, universal format: a string. JSON is that format. It looks almost identical to a JavaScript object, but it's just plain text.

Why is it important?

Think of it as the universal shipping container of the web. Every programming language (Python, Java, Ruby, etc.) knows how to read and write JSON. This means a server written in Python can easily send data to a client written in JavaScript. It's the common ground that makes the web work.

How do we use it?

JavaScript gives us two key methods:

  • JSON.stringify(): Takes a JavaScript object and turns it into a JSON string, ready to be sent to a server.
  • JSON.parse(): Takes a JSON string (received from a server) and turns it back into a usable JavaScript object.

// A JavaScript object
const user = {
    name: "Ada Lovelace",
    id: 1815,
    isDeveloper: true
};

// 1. Stringify it to send over the network
const jsonString = JSON.stringify(user);
console.log(jsonString); 
// Output: "{\"name\":\"Ada Lovelace\",\"id\":1815,\"isDeveloper\":true}"

// 2. Parse it when you receive it from a server
const receivedString = '{"name":"Grace Hopper","id":1906,"isDeveloper":true}';
const userObject = JSON.parse(receivedString);
console.log(userObject.name); 
// Output: Grace Hopper

When you use fetch(), you'll often use the .json() method on the response, which is a convenient shortcut for parsing the JSON string for you.

Fetching with .then() vs. modern async/await

What's the difference?

Both are ways to handle asynchronous operations—actions that take time, like fetching data. You can't just stop your entire program to wait for a network request to finish. That would freeze the user's browser!

.then() (The Classic Way): This is the original Promise-based syntax. You "chain" functions onto your fetch call. The first .then() runs when the initial response comes back, and the second .then() runs when the data is fully processed. It's a chain of "do this, *then* do that, *then* do that."

async/await (The Modern Way): This is "syntactic sugar" built on top of Promises. It lets you write asynchronous code that *looks* synchronous (like it's running line-by-line). The async keyword tells JavaScript that a function will contain asynchronous operations. The await keyword tells JavaScript to pause the function's execution at that line until the Promise resolves, and then continue.

Why prefer async/await?

Readability. It's simply easier for human brains to follow. The code is cleaner, less nested, and resembles the step-by-step logic we're used to. Error handling with try...catch is also far more intuitive than the .catch() block in a promise chain.

How do they compare?

Here is the exact same logic, written in both styles. Notice how much cleaner the async/await version is.

Classic .then() chain:


function getUserWithThen() {
  const url = 'https://api.github.com/users/octocat';
  
  fetch(url)
    .then(response => {
      // First, we get the response headers, but not the data yet.
      // We need to tell it to parse the body as JSON.
      return response.json(); 
    })
    .then(data => {
      // Now we have the actual data!
      console.log(data);
    })
    .catch(error => {
      // This will catch network errors.
      console.error('Something went wrong:', error);
    });
}

Modern async/await:


async function getUserWithAsyncAwait() {
  const url = 'https://api.github.com/users/octocat';
  
  try {
    // Await pauses the function until the fetch is complete.
    const response = await fetch(url); 
    
    // Await pauses again until the JSON is parsed.
    const data = await response.json(); 
    
    // Now we have the data, and the code looks clean.
    console.log(data);
  } catch (error) {
    // A single, clean catch block for any errors in the try block.
    console.error('Something went wrong:', error);
  }
}

Mission 2: The Errors

What are Promises?

What is a Promise?

A Promise is a special JavaScript object that represents the eventual completion (or failure) of an asynchronous operation. When you call an async function like fetch(), it doesn't immediately return the data. It can't—the data is still on a server across the world! Instead, it immediately returns a Promise. It's a "promise" that it will give you a value back... eventually.

A Promise exists in one of three states:

  • Pending: The initial state. The operation hasn't finished yet. You're waiting for your package to arrive.
  • Fulfilled (or Resolved): The operation completed successfully. The Promise now has a value. Your package arrived safely!
  • Rejected: The operation failed. The Promise has a reason for the failure (an error). The package was lost in transit.

Why are they fundamental?

They are the bedrock of modern asynchronous JavaScript. They provide a clean and manageable way to handle operations that take time, preventing tangled messes of nested callbacks (more on that later). The async/await syntax you love is just a way to work with Promises more elegantly.

How do we see them?

If you forget to use await, you'll see the Promise object itself logged to the console. This is a classic beginner mistake, so pay attention!


async function checkPromise() {
  const response = fetch('https://api.github.com/users/octocat');
  console.log(response); // This will log: Promise { <pending> }
  
  // To get the actual value, you MUST wait for it.
  const resolvedResponse = await fetch('https://api.github.com/users/octocat');
  console.log(resolvedResponse); // This logs the Response object.
}

checkPromise();

Handling Rejected Promises (try...catch)

What is try...catch?

A try...catch block is JavaScript's primary mechanism for error handling. It allows you to "try" a block of code that might fail. If an error occurs (i.e., a Promise is rejected) inside the try block, the code execution immediately jumps to the catch block, where you can handle the error gracefully instead of crashing your application.

Why is it essential for async/await?

When you await a Promise, if that Promise rejects, it "throws an error." The try...catch block is how you catch that thrown error. Without it, a rejected promise will result in an "Uncaught (in promise)" error, which is a silent but deadly bug in your application.

Rule of thumb: If you use await, you should almost always have it wrapped in a try...catch block.

How do we use it?

Simply wrap your "happy path" code in the try block and your error handling logic in the catch block. The catch block receives an `error` object that contains information about what went wrong.


async function fetchFromBrokenUrl() {
  // This URL doesn't exist and will cause a network error.
  const apiUrl = 'https://thissitedoesnotexist.fail/api';

  try {
    console.log("Trying to fetch...");
    const response = await fetch(apiUrl); // This line will fail.
    const data = await response.json();   // This line will never be reached.
    console.log("Success:", data);
  } catch (error) {
    // Execution jumps here immediately after the fetch fails.
    console.error("Oh no, an error occurred!");
    console.error(error.message); // e.g., "Failed to fetch"
  } finally {
    // (Optional) This block runs regardless of success or failure.
    console.log("Fetch attempt finished.");
  }
}

The response.ok Gotcha

What's the "gotcha"?

This is one of the most confusing parts of fetch() for beginners. A fetch() Promise only rejects if there's a network error. For example, the user is offline, the domain doesn't exist, or there's a CORS issue.

However, if the request successfully reaches the server, but the server responds with an error code like 404 Not Found or 500 Internal Server Error, the fetch() Promise will be FULFILLED, not rejected. Your catch block will NOT run!

Why does it work this way?

Because a 404 is a valid, successful HTTP response. The network connection worked perfectly. The server received your request and successfully responded, "Hey, I looked for that thing you wanted, and I couldn't find it." From a networking perspective, everything is fine.

How do we handle it properly?

The `Response` object that fetch() resolves with has a handy boolean property called response.ok. This property is true only for successful HTTP status codes (200-299). For any other code (like 404 or 500), it will be false. We must manually check this property and throw our own error to trigger the catch block.


async function fetchNonExistentUser() {
  // This user likely does not exist, so the GitHub API will return a 404.
  const apiUrl = 'https://api.github.com/users/this-user-does-not-exist-123456';

  try {
    const response = await fetch(apiUrl);

    console.log('Response OK:', response.ok); // This will be false
    console.log('Response Status:', response.status); // This will be 404

    // THE CRITICAL CHECK!
    if (!response.ok) {
      // If the response is not ok, we create and throw an error.
      // This will stop the 'try' block and trigger the 'catch' block.
      throw new Error(`HTTP error! Status: ${response.status}`);
    }

    const data = await response.json();
    console.log(data);

  } catch (error) {
    // Now our catch block works for both network errors AND HTTP errors!
    console.error("Safely caught the error:", error.message);
  }
}

fetchNonExistentUser();

Mission 3: The Deep Dive

Escaping Callback Hell

What is Callback Hell?

Before Promises, the only way to handle async operations in JavaScript was with callback functions. A callback is a function you pass into another function, which then gets "called back" when the operation is complete. This is fine for one operation. But what if you need to do a second operation based on the result of the first, and a third based on the result of the second?

You end up with nested callbacks, creating a deeply indented, right-drifting structure known as the "Pyramid of Doom" or "Callback Hell." It's incredibly difficult to read, reason about, and debug.

Why did we need to escape?

Code that is hard to read is hard to maintain. Callback Hell makes error handling a nightmare, as you need separate error handlers for each nested level. It violates the core principle of writing clean, linear, and understandable code.

How do Promises and async/await save us?

Promises flatten the pyramid. Instead of nesting, you chain .then() calls. This is a huge improvement. But async/await is the ultimate escape. It allows us to write asynchronous code that reads as if it were a simple, synchronous, top-to-bottom script. It completely eliminates the "Pyramid of Doom."

Example of Callback Hell (hypothetical):


// Don't write code like this! This is for demonstration only.
getUser(1, (error, user) => {
  if (error) {
    handleError(error);
  } else {
    getPosts(user.id, (error, posts) => {
      if (error) {
        handleError(error);
      } else {
        getComments(posts[0].id, (error, comments) => {
          if (error) {
            handleError(error);
          } else {
            console.log(comments);
          }
        });
      }
    });
  }
});

The Glorious async/await Escape:


async function getCommentsForUser() {
  try {
    const user = await fetchUser(1);
    const posts = await fetchPosts(user.id);
    const comments = await fetchComments(posts[0].id);
    console.log(comments);
  } catch (error) {
    handleError(error);
  }
}

The difference is night and day. The intent of the code is crystal clear, and error handling is centralized and simple.

Working with multiple APIs using Promise.all()

What is Promise.all()?

Promise.all() is a powerful method that takes an array of Promises as input. It returns a single new Promise that fulfills when all of the input Promises have fulfilled. The fulfilled value of this new Promise is an array containing the fulfilled values of the input Promises, in the same order.

If any of the input Promises reject, the entire Promise.all() immediately rejects with the reason of the first Promise that rejected.

Why is it so useful?

Efficiency! Imagine you need data from three different, independent API endpoints. The naive approach would be to await them one by one:


// SLOW and INEFFICIENT way
const user = await fetch('.../user/1');  // waits ~300ms
const products = await fetch('.../products'); // waits another ~400ms
const settings = await fetch('.../settings'); // waits another ~200ms
// Total time: ~900ms

This is a waste of time! Since none of these requests depend on each other, we can fire them all off at the same time and wait for them all to come back. This is concurrency. Promise.all() allows us to do exactly that.

How do we use it?

You start all the fetch requests without await, which gives you an array of pending Promises. Then, you pass that array to Promise.all() and await the result.


async function fetchAllData() {
  const userUrl = 'https://api.github.com/users/octocat';
  const reposUrl = 'https://api.github.com/users/octocat/repos';
  const orgsUrl = 'https://api.github.com/users/octocat/orgs';

  try {
    // Start all fetch requests at once. This returns an array of Promises.
    const promises = [
      fetch(userUrl),
      fetch(reposUrl),
      fetch(orgsUrl)
    ];

    // Wait for ALL promises in the array to resolve.
    const responses = await Promise.all(promises);

    // Check all responses for errors.
    for (const res of responses) {
        if (!res.ok) {
            throw new Error(`HTTP error on URL ${res.url}! Status: ${res.status}`);
        }
    }
    
    // Now, parse all the JSON bodies. This also returns an array of Promises!
    const jsonPromises = responses.map(response => response.json());

    // Wait for all the JSON parsing to complete.
    const [userData, reposData, orgsData] = await Promise.all(jsonPromises);

    // Now you have all your data!
    console.log('User:', userData.name);
    console.log('Number of Repos:', reposData.length);
    console.log('Number of Orgs:', orgsData.length);
    
  } catch (error) {
    console.error("Failed to fetch all data:", error);
  }
}

fetchAllData();
// This will be much faster than fetching them sequentially.
// The total time will be roughly the time of the SLOWEST single request.

Micro-Challenge: Concurrent Fetches

Your final micro-challenge is to fetch data for three different GitHub users simultaneously: "wesbos", "kentcdodds", and "getify".

Use Promise.all() to fetch all three at once. After they have all successfully returned, create an array of just their names (e.g., ["Wes Bos", "Kent C. Dodds", "Kyle Simpson"]) and log it to the console.

Show Solution 

async function fetchTrio() {
  const usernames = ['wesbos', 'kentcdodds', 'getify'];
  const baseApiUrl = 'https://api.github.com/users/';

  try {
    // Create an array of fetch promises
    const fetchPromises = usernames.map(username => 
      fetch(`${baseApiUrl}${username}`)
    );
    
    // Wait for all initial responses
    const responses = await Promise.all(fetchPromises);

    // Check for any failed responses
    for (const res of responses) {
      if (!res.ok) {
        throw new Error(`Failed to fetch ${res.url}: ${res.statusText}`);
      }
    }

    // Create an array of json-parsing promises
    const jsonPromises = responses.map(res => res.json());
    
    // Wait for all json parsing to complete
    const users = await Promise.all(jsonPromises);

    // Map the final array of user objects to an array of just their names
    const names = users.map(user => user.name);

    console.log("Fetched these developers concurrently:", names);
    // Expected output: ["Wes Bos", "Kent C. Dodds", "Kyle Simpson"]

  } catch (error) {
    console.error("An error occurred:", error);
  }
}

// Let's run it!
fetchTrio();

Mission 4: Final Project - GitHub Dev Tracker

Architectural Breakdown

Congratulations, you've mastered the core concepts. It's time to put it all together. We're going to build a simple but powerful "GitHub Dev Tracker" application using only vanilla JavaScript. This project will test everything you've learned: fetching data, handling user input, robust error handling, and manipulating the DOM.

This is not a step-by-step code-along. This is an architectural brief, like you'd get in a real-world developer role. It's your job to translate these steps into code.

Step 1: The HTML Structure (The "Bones")

Keep it simple. You need three core elements:

  • An <input type="text"> where the user can type a GitHub username. Give it a clear id like username-input.
  • A <button> to trigger the search. Give it an id like search-button.
  • A container <div> where the results will be displayed. This is your canvas. Give it an id like profile-container. It should be empty initially. You can also add a loading state element and an error message element inside it.

Step 2: The Event Listener (The "Nervous System")

In your JavaScript, you need to "listen" for the user's action.

  • Get references to your input, button, and container elements using document.getElementById().
  • Add a 'click' event listener to your search button.
  • When the button is clicked, the callback function should:
    1. Get the value from the username input field (and maybe .trim() it to remove whitespace).
    2. If the input is empty, do nothing or show a small warning.
    3. If the input has a value, call your main data-fetching function (which you'll build in the next step), passing the username to it.

Step 3: The Async Fetch Function (The "Heart")

This is the core of your application. Create an async function, maybe called fetchGitHubUser(username).

  • Construct the URL: The GitHub API endpoint is https://api.github.com/users/USERNAME. Use a template literal to insert the `username` argument.
  • Wrap in try...catch: This is non-negotiable. All your fetching logic goes inside the try block.
  • Fetch and Check: await the fetch call. Immediately after, you MUST check if (!response.ok). If it's not okay (e.g., a 404 for a user not found), throw a new error with a descriptive message like "User not found!". This will send control to your catch block.
  • Process Data: If the response is ok, await the response.json() call to get the user data.
  • Call the Renderer: Once you have the data, pass it to another function responsible for updating the UI (e.g., renderProfile(data)).
  • Handle Errors: The catch block should receive the error. It should call a UI function to display the error message to the user (e.g., renderError(error.message)).

Step 4: The DOM Manipulation (The "Face")

Create separate functions for updating the UI. This keeps your logic clean (separation of concerns).

  • renderProfile(data):
    1. First, clear any previous content from your profile-container. Set its innerHTML = ''.
    2. Create new elements using document.createElement(). You'll need an <img> for the avatar and a <p> or <h3> for the name and bio.
    3. Set their properties: img.src = data.avatar_url, p.textContent = data.bio, etc.
    4. Append these new elements to your profile-container.
  • renderError(message):
    1. Clear the profile-container.
    2. Create a new element, like a <p>.
    3. Set its text content to the error message.
    4. Give it a class for styling (e.g., class="error-message" so you can make it red with CSS).
    5. Append it to the profile-container.
  • (Optional) renderLoading(isLoading): Before you start the fetch, you can call this to show a "Loading..." message. When the fetch is complete (in a finally block perhaps), you call it again to hide the message.

You have all the knowledge. Now, build it. This is your final test. Show me you've been paying attention. Good luck.
